These recipes prepare requests immediately before Noodle sends them. Start with
[Pre-request Scripting](/docs/guides/pre-request-scripting/) if you are new to
`scripts.pre`. Every recipe here uses the current **pre-request** runtime. We
will add post-request recipes when post-request scripting is available.

## Before you start

Copy a request into a `.yml` file in your collection, then adapt the example
endpoint and fields to your API. All endpoints below use `api.example.com` as a
placeholder. Scripts belong to individual requests; there is no collection-wide
script or shared JavaScript context.

Prefer saved request fields and `$VARNAME` substitution for static values. Use
[captures](/docs/guides/automation/#pass-response-values-forward) to save response
values and [assertions](/docs/guides/automation/#put-success-criteria-beside-the-request)
to check responses. You do not need a script for those jobs.

Keep these execution rules in mind:

- Environment and RunScope substitution happens **before** the script. Script
  source itself is literal: read inputs with `env.get()` or `run.get()`.
- Apply a newly generated value directly to the current request. `run.set()`
  makes it available for substitution in later requests in the same run.
- Each script runs in a fresh synchronous sandbox. Imports, network calls,
  filesystem access, timers, and asynchronous work are unavailable.
- If a script fails, Noodle discards its request and RunScope changes and skips
  HTTP. Successful request changes are never written back to YAML.

See the [API reference](/docs/reference/collection-format/#sandboxed-pre-request-script)
for every supported method and resource limit. Review scripts before running
them: `env.get()` can read secrets from the selected environment. Keep secret
values out of log messages.

## Timestamps

Use this when an API expects the current time in a header or event payload.
This request needs no environment values and starts with a JSON object body.

```yaml
name: Create timestamped event
method: POST
url: https://api.example.com/events
body_type: json
body: '{"event":"deployment"}'
scripts:
  pre: |-
    const now = new Date();
    const timestamp = now.toISOString();
    const unixSeconds = Math.floor(now.getTime() / 1000);
    request.headers.set("X-Timestamp", timestamp);
    request.body.setJson({
      ...request.body.json(),
      created_at: timestamp,
      timestamp: unixSeconds,
    });
```

The outgoing header and `created_at` field contain the same UTC ISO timestamp.
The numeric `timestamp` field uses Unix **seconds**. Use `now.getTime()` when
your API expects milliseconds. These values use your machine's clock, so keep
it synchronized if the server checks timestamp freshness.

## Identifiers and nonces

Use a request ID for correlation and a random nonce when your API requires one.
This example generates a UUID v4 and a separate 16-byte nonce without any
environment inputs.

```yaml
name: Check health with a request ID
method: GET
url: https://api.example.com/health
scripts:
  pre: |-
    const hex = crypto.randomBytes(16, "hex");
    const variant = (8 + (parseInt(hex[16], 16) & 3)).toString(16);
    const requestId = [
      hex.slice(0, 8),
      hex.slice(8, 12),
      "4" + hex.slice(13, 16),
      variant + hex.slice(17, 20),
      hex.slice(20),
    ].join("-");
    request.headers.set("X-Request-ID", requestId);
    request.headers.set("X-Nonce", crypto.randomBytes(16, "hex"));
```

`X-Request-ID` has the standard UUID v4 format and `X-Nonce` has 32 hexadecimal
characters. Both are generated again on each send. If your API accepts any
opaque request ID, `crypto.randomBytes(16, "hex")` is enough by itself.
`crypto.randomUUID()` is not part of Noodle's sandbox API.

## Idempotency keys

Use this for a **new operation** when the server supports an `Idempotency-Key`
header. The script generates a random key only when the prepared request does
not already contain one.

```yaml
name: Create order with an idempotency key
method: POST
url: https://api.example.com/orders
body_type: json
body: '{"product_id":"demo-product","quantity":1}'
scripts:
  pre: |-
    if (!request.headers.has("Idempotency-Key")) {
      request.headers.set("Idempotency-Key", crypto.randomBytes(16, "hex"));
    }
```

Without a saved key, every send gets a new 32-character hexadecimal key and
represents a new operation. This script does not make repeated manual sends
safe retries automatically. For retries of the **same** operation, configure
the same non-empty header value in your saved request or folder headers; the
script preserves it. Use a different key for a different operation and follow
your server's rules for expiration and payload matching.

## Dynamic JSON bodies

Use this to create fresh test data and remove a local fixture field before
sending. The saved body must be a JSON object; no environment inputs are needed.

```yaml
name: Create customer with fresh test data
method: POST
url: https://api.example.com/customers
body_type: json
body: '{"name":"Cookbook Customer","_fixture":"customer-smoke"}'
scripts:
  pre: |-
    const body = request.body.json();
    delete body._fixture;
    body.email = "cookbook+" + crypto.randomBytes(8, "hex") + "@example.com";
    body.created_at = new Date().toISOString();
    request.body.setJson(body);
```

The outgoing body retains `name`, adds a generated email and timestamp, and
omits `_fixture`. The saved YAML remains unchanged. Use synthetic data like this
against your test API, and clean up created resources as your workflow requires.

## Dynamic query parameters

Use this to fetch events from a rolling time window instead of updating saved
dates by hand. The optional environment value `LOOKBACK_HOURS` defaults to `24`.
If supplied, it must be a positive number that produces a valid start date.

```yaml
name: List recent events
method: GET
url: https://api.example.com/events
scripts:
  pre: |-
    const hours = Number(env.get("LOOKBACK_HOURS") ?? "24");
    if (!Number.isFinite(hours) || hours <= 0) {
      throw new Error("LOOKBACK_HOURS must be a positive number");
    }
    const to = new Date();
    const from = new Date(to.getTime() - hours * 60 * 60 * 1000);
    if (!Number.isFinite(from.getTime())) {
      throw new Error("LOOKBACK_HOURS produces an invalid start date");
    }
    request.params.set("from", from.toISOString());
    request.params.set("to", to.toISOString());
    request.params.append("tag", "deployment");
    request.params.append("tag", "release");
```

The request sends `from` and `to` in UTC, plus two `tag` query values. Noodle
handles query encoding. `set()` replaces enabled parameters with the same
case-sensitive name; `append()` adds another enabled value. Disabled entries
are preserved. Remove the tag lines if your API does not accept repeated tags.

## Validate before sending

Use this when missing credentials or invalid input should stop a request
locally. This example requires environment values `ACCOUNT_ID` and `API_TOKEN`,
and a JSON object body with a positive integer `amount` in minor currency units.

Set up the inputs in an existing `development` environment of your collection:

```bash
noodle environment set ACCOUNT_ID demo-account --collection ./api --env development
noodle secret set API_TOKEN --collection ./api --env development
```

The secret command prompts for the token without echoing it. Keep real tokens
in secret storage, and select `development` when running the example.

```yaml
name: Create validated payment
method: POST
url: https://api.example.com/payments
body_type: json
body: '{"amount":1250,"currency":"USD"}'
scripts:
  pre: |-
    const accountId = env.get("ACCOUNT_ID");
    const token = env.get("API_TOKEN");
    if (!accountId || !accountId.trim()) {
      throw new Error("ACCOUNT_ID is required");
    }
    if (!token || !token.trim()) {
      throw new Error("API_TOKEN is required");
    }
    const body = request.body.json();
    if (!body || typeof body !== "object" || Array.isArray(body)) {
      throw new Error("Payment body must be a JSON object");
    }
    if (!Number.isSafeInteger(body.amount) || body.amount <= 0) {
      throw new Error("amount must be a positive safe integer in minor units");
    }
    request.body.setJson({ ...body, account_id: accountId });
    request.auth.setBearer(token);
```

Valid inputs add `account_id` to the outgoing body and set bearer authentication.
The auth helper replaces the complete prepared auth configuration. Missing
inputs or an invalid amount fail the script and skip HTTP. Error messages name
the invalid field without including its value.

This is a preparation check, not a substitute for server-side validation.
If your saved request references a missing `$VARNAME`, substitution fails before
the script runs; read a value with `env.get()` when you need a custom script error.

## Hashing and signing

Use this when the API expects a digest or HMAC signature. Configure
`SIGNING_SECRET` in the selected environment through secret storage:

```bash
noodle secret set SIGNING_SECRET --collection ./api --env development
```

This example illustrates a **generic** protocol: hash the final UTF-8 body with
SHA-256, and sign the string `timestamp + "." + body` with HMAC-SHA256. Both
outputs are hexadecimal. Adapt the header names, encoding, and signed message
to your server's specification.

```yaml
name: Create signed event
method: POST
url: https://api.example.com/events
body_type: json
body: '{"event":"deployment","service":"api"}'
scripts:
  pre: |-
    const secret = env.get("SIGNING_SECRET");
    if (!secret || !secret.trim()) {
      throw new Error("SIGNING_SECRET is required");
    }
    const timestamp = new Date().toISOString();
    request.body.setJson({ ...request.body.json(), created_at: timestamp });
    const body = request.body.text();
    request.headers.set("X-Timestamp", timestamp);
    request.headers.set("X-Content-SHA256", crypto.sha256(body, "hex"));
    request.headers.set(
      "X-Signature",
      crypto.hmacSha256(secret, timestamp + "." + body, "hex"),
    );
```

The digest and signature each have 64 hexadecimal characters. The signature
covers the timestamp and the final body, including `created_at`. Do all body
mutations **before** computing either value, and do not reformat the body
afterward. The server must verify the same bytes and implement its own timestamp
freshness and replay rules. An unkeyed SHA-256 digest alone does not authenticate
the request.

These helpers hash UTF-8 strings. `request.body.text()` cannot read multipart,
URL-encoded, or binary bodies, so this recipe uses a textual JSON body. Scripts
cannot fetch signing keys or access files.

## Share data across requests

Use this when several requests in one collection run need the same generated
test data. This two-request workflow creates a customer, then looks it up by
email. It needs no environment inputs. Put both files in your collection and
ensure **Create customer** precedes **Find customer** in collection order.

Save the first request as `customers/create.yml`:

```yaml
name: Create customer
method: POST
url: https://api.example.com/customers
body_type: json
body: '{"name":"Cookbook Customer"}'
scripts:
  pre: |-
    const email = "cookbook+" + crypto.randomBytes(8, "hex") + "@example.com";
    run.set("customer_email", email);
    request.body.setJson({ ...request.body.json(), email });
```

The first request sets the shared value and writes it directly into its body.
Save the later request as `customers/find.yml`. It can use ordinary substitution:

```yaml
name: Find customer
method: GET
url: https://api.example.com/customers
params:
  - name: email
    value: $customer_email
```

Run them together with the CLI or the TUI Runner:

```bash
noodle collection run ./api customers/create customers/find
```

Selected requests execute in collection order. The second request sends the same
email as the first. `run.get("customer_email")` reads it from a later script;
`run.unset("customer_email")` removes it from the transient scope.

`run.set()` commits when the script succeeds, before HTTP. The email remains
available even if customer creation later fails, so add suitable assertions and
use `--fail-fast` if later requests depend on a successful creation.

The value disappears when the collection run ends. Separate manual sends and
`request run` calls have isolated scopes, so they cannot share this value. Do
not put `$customer_email` in the first request: its substitution would run before
the script creates the variable. Use a [capture](/docs/guides/automation/#pass-response-values-forward)
when you need a server-generated customer ID instead.

## Inspect results

The TUI **Results** tab shows script status, errors, and redacted logs. Human CLI
output reports status and log count; `--json` includes the redacted `scripts`
result group. See [Inspect script results](/docs/guides/pre-request-scripting/#inspect-script-results)
for details. Script source, results, logs, and RunScope values do not enter
timeline history, while successful manual sends store the prepared request
snapshot after normal timeline redaction.
